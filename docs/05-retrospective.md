# 05 - 复盘（回顾）

## 最难的三个问题

1. 预算判断放在哪一层？  
一开始很容易让 `estimate_cost` 顺便判断超不超预算，甚至在工具里直接改成 lite。那样「看到 12 再改选 8」会变成工具或图边上的固定分支，对不上题目里的 ReAct 要求。最后估价只返回分项、合计和耗时；比预算、换档、算缺口都留在模型下一步。路由函数里不出现 `budget`、`lite`、`standard`。代价是模型必须自己读 `total`。收益是 `examples/budget-overrun/trace.json` 里，估价 12 之后的下一步是对 lite 调用 `generate_script`，依据写的是超出预算 10。

2. 失败步骤怎样保留、又不把失败写成成功？  
题目要求部分成功时留下已完成步骤，失败不能改成成功。如果只看最终有没有草稿，第一次失败会被第二次成功盖掉。步骤按观察逐条记：`examples/tool-failure/` 里同一轮先有 `estimate_cost` 的 `failed`，再有一次 `success`。过程中还有一个真实问题：命令行按用例名复用 SQLite 会话，前一次失败步骤叠进后面的 `normal`，被误判成 `tool_failed`。修法是日常验收开新会话，只有显式 `--thread-id` 才写检查点。这也说明「失败不虚报」要靠运行和断言盯住，不能只写在提示词里。

3. 什么失败值得再试一次？  
加分是工具失败后调整计划，不是所有失败都重试。检索不到主题是确定性结果，再搜也没有。`estimate_cost` 的瞬时不可用才值得再调一次。注入开关只挂在 `tool-failure` 上，避免正常完成也被第一次估价打断。Mock 看到失败后停止，用来验收「失败保持 failed」。真实模型在同一次运行里再次估价并保存，这条路径写在同一份 Trace 里。连续失败则停止，已成功的检索和脚本仍保留。

## 学习收获

- 事实和选择要分开。工具给费用、素材和成败；超没超预算、换不换档、要不要再试，由模型根据当次观察决定。这是 ReAct 能被 Trace 审计的原因。
- 提示词和工具定义是两套东西。提示词规定角色和何时调用；工具自己带名称、说明和 JSON Schema。把提示词改成工具清单，模型就没有停止条件。
- 结构比口头约束可靠。超预算不能入库靠 `save_plan`；失败不被抹掉靠逐步记录；检查点污染靠新会话隔离。这些都不依赖模型自觉。

## 下一步（按优先级）

1. 给决策质量建立回归评测。目前判断「超预算改选 lite」「失败后重试且保留 failed」是否正确，靠人工看 Trace。下一步把七组用例扩成评测集：同一用例重复运行多次，统计关键决策的出现率（改选正确率、失败恢复率、无草稿时误报完成率），用 pytest 断言。这样提示词、模型或工具改动后，能立刻发现决策退化，而不是等评审发现问题。

2. 量化真实模型的路径稳定性。Mock 每次走同一条路；真实模型有非确定性。同一输入用 `--model api` 重复运行，统计路径分布和步数分布，结论写进 `docs/03-evaluation.md`。如果路径发散，再评估收紧提示词或固定采样参数，而不是靠一次运行的 Trace 下结论。

3. 规则收敛到单一来源。把 `rules.json` 的 `constraints` 注入系统提示，避免同一条规则写在 JSON 和手写提示词两处。将来改规则时只动一处，减少两处不同步导致模型行为漂移的风险。

4. 让耗时参与提前决策。目前 `hours` 只在 `save_plan` 里拦截超时，模型要先经历一次注定失败的保存。改进方向是在估价返回后把「耗时与截止时间的比较」写进工具提示，让模型在保存前就改选更短方案，把一次失败试错变成一次正确决策。

5. 扩大决策空间。现在只有 standard / lite 两档、单一素材组合，改选问题偏简单。增加素材组合与方案档位后，「超预算后选哪套」才接近真实规划问题，也能检验评测集是否真的约束住模型。
